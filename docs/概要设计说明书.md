# 系统概要设计说明书

| 项目 | 内容 |
|---|---|
| 项目名称 | 医疗运营数据主题分析平台 |
| 文档版本 | V1.1 |
| 设计基线 | `docs/需求规格说明书.md` V1.1 |
| 日期 | 2026-11-20 |
| 架构风格 | 单体分层架构 + 文件型批量数仓 |

## 1. 设计目标

1. 用一套可运行、可复现的工程展示医疗多源数据从接入、治理、建模、指标服务到可视化的完整链路。
2. 数仓分层边界清晰，DWD 不再暴露直接患者身份，指标口径集中管理。
3. 前后端职责分离，所有业务接口有统一认证、授权、响应和 Trace ID。
4. 演示环境低依赖、可离线运行；生产化接口保留但不在课程初版冒充已实现。
5. 对数据量、DRG 口径、床位/人力、LLM 等能力明确标注边界，避免过度设计或虚假结论。

## 3. 技术选型

| 层 | 选型 | 选择理由 | 边界 |
|---|---|---|---|
| 前端 | Vue 3 + Vue Router + Vite | 组件化、路由清晰、构建快 | 未使用 Pinia、axios、UI 组件库 |
| 图表 | ECharts 6 | 医疗看板常用、支持折线/柱/饼和交互 | 通用组件只有1个，配置由工厂生成 |
| 后端 | FastAPI + Pydantic | OpenAPI 自动生成、类型校验、开发效率高 | 单体服务，未拆分微服务 |
| 认证 | PyJWT + PBKDF2 | 无额外服务依赖，满足课程 RBAC | 无刷新令牌、限流、密钥轮换 |
| 数仓 | SQLite WAL | 零安装、便于课程演示和复现 | 非生产 MPP，未验证 PostgreSQL |
| ETL | Python csv/openpyxl | 直接处理文件、错误行可反馈 | 批量文件，不是 CDC/流式 |
| 报表 | openpyxl + reportlab | 生成真实 XLSX/PDF | 模板样式为教学版 |
| 智能分析 | DeepSeek/Kimi OpenAI兼容接口 | 用户指定模型；可离线回退 | 外部调用未实测；不是自由 NL2SQL |
| 部署 | Docker Compose + Nginx | 一键演示、前后端代理 | 当前环境无 Docker，仅配置 |

## 4. 分层设计

### 4.1 ODS

- `etl_batch`：批次状态、源文件、SHA-256、行数、错误、消息。
- `ods_record`：源表名 + 业务主键唯一，保留原行 JSON 和内容哈希。
- 设计取舍：保留原文便于追溯，但增加敏感数据保护要求。

### 4.2 DWD

六张标准化明细表：门诊、住院、收费、EMR、LIS、财务。共同规则：

- 日期统一 `YYYY-MM-DD`，数值统一 REAL。
- 业务主键唯一，`INSERT OR REPLACE` 幂等。
- 直接身份字段不进入 DWD，使用加盐 `patient_key`。
- `dwd_encounter_wide` 统一门诊/住院就诊粒度，汇总EMR、LIS和收费信息，当前10,500行；不替代六张按源标准表。
- 错误行不中断整批，按行收集原因并写入批次消息。

### 4.3 DIM

- `dim_department`：科室、教学床位、教学人力、映射状态。
- `dim_disease`：10 个教学病种。
- `dim_fee_type`：9 个收费类别。
- `dim_date`：日期、年季月、周起始、ISO 年周、周末标记。

### 4.4 DWS

公共汇总 `dws_dept_day` 和 `dws_disease` 作为服务层基础，另有八张物理主题集市：

1. `dws_outpatient_day`
2. `dws_inpatient_day`
3. `dws_revenue_day`
4. `dws_drug_day`
5. `dws_consumable_day`
6. `dws_disease_day`
7. `dws_resource_day`
8. `dws_service_day`

主题集市由公共汇总和维表重建，保证同一口径；组合主键防重。

### 4.5 ADS

`ads_metric_result(metric_code, stat_date, grain, dept_code, value_num, batch_id, calculated_at)`：

- 粒度：day/week/month。
- 范围：每个科室 + 全院 `ALL`。
- 当前预存全部30项可算指标，共35,640行。
- 周桶以周一为起点，月桶以自然月首日为起点。
- 区间回刷按完整桶删除并重算，重复执行幂等。

## 6. 关键流程

### 6.1 ETL

```text
读取文件 → 模板识别 → 必填字段校验 → 行级标准化
→ 主键去重/冲突检测 → ODS原文 → DWD明细 → 批次和质量记录
→ 重建DWS/ADS → 返回行数、错误与批次ID
```

### 6.2 指标查询

```text
用户/角色 → 日期归一 → 科室范围校验 → 指标服务
→ DWS/DWD参数化SQL → 零分母处理 → 统一响应
```

### 6.3 智能问数

```text
问题长度/危险词检查 → 指标最长别名匹配 → 科室识别
→ 时间解析 → 指标服务取数 → 可选LLM解读 → 图表数据返回
```

`/ai/ask` 不执行模型生成SQL；模型不可用时返回 `local-rules` 或 `local-rules-fallback`。另有 `/ai/nl2sql` 对模型生成的单条聚合SELECT执行表/列白名单、写操作拒绝和只读事务，真实模型生成待Key验证。

### 6.4 报表

```text
周期解析 → 指标汇总 → 科室Top/结构 → 异常阈值提示
→ 章节对象 → 前端渲染 / PDF服务端生成
```

## 8. 安全设计

- 密码 PBKDF2 加盐散列，不存明文。
- JWT HS256，令牌包含用户名、角色、过期时间。
- 服务端角色依赖与科室范围双重校验，前端筛选不作为授权依据。
- 登录、导入、ETL、质量、查询、导出、AI 写审计。
- 危险问数拦截写 SQL 关键词、身份证/手机号模式和患者姓名等。
- 患者标识单向散列；ODS 原文访问需文件级权限。
- 当前安全缺口：默认口令、无 HTTPS、无登录限流、无密钥轮换、无渗透测试。

## 9. 部署设计

```text
浏览器 → Nginx(5173) → 静态SPA
                    └→ /api、/health、/docs → FastAPI(8765)
FastAPI → /app/data/derived/medical_ops.db（命名卷）
```

- 后端容器启动前执行全量 ETL；也可手动执行 CLI。
- 前端多阶段构建为静态文件。
- 当前环境无 Docker，容器构建、代理、持久化和恢复未实测。

## 10. 关键设计决策

| 决策 | 原因 | 代价 |
|---|---|---|
| SQLite 而非 PostgreSQL | 课程环境低依赖、单文件可交付 | 并发/分析能力有限 |
| 全量重建 DWS/ADS | 逻辑简单、可复现 | 数据量大时耗时 |
| ADS 三粒度预计算 | 看板查询稳定、可对账 | 存储增加，回刷需完整桶 |
| 指标目录代码化 | 统一口径、可测试 | 新增指标需改代码与文档 |
| 不执行自由 SQL | 安全边界清晰 | 未满足“自由 NL2SQL”课程表述 |
| 主题 DWS 从公共汇总派生 | 避免多套口径漂移 | 主题定制能力有限 |
| LLM 只做解读 | 无Key可运行、保护数据 | 不是生成式取数 |

## 11. 设计边界

- 不是生产级医疗数据平台，不连接真实 HIS。
- 不提供临床诊断或治疗建议。
- DRG/DIP、床位、人力为教学估算，不可作为绩效依据。
- 不支持 12 个月以外的数据自动生成；最终数据范围以验收补充为准。
- 不支持多租户、高可用、实时流、CDC、消息队列。
