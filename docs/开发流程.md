# 项目开发流程

| 项目 | 内容 |
|---|---|
| 项目名称 | 医疗运营数据主题分析平台 |
| 文档版本 | V1.0 |
| 日期 | 2026-11-20 |
| 适用范围 | 课程项目从需求到归档的全过程 |

## 1. 流程总览

```text
需求基线 → 设计评审 → 任务拆分 → 开发与环境准备
→ 数据接入/数仓/指标/服务/前端 → 自测与代码评审
→ 集成测试与验收 → 部署试运行 → 归档总结
```

每个阶段必须有可检查的输入、输出和退出条件；未通过退出条件不得把状态标记为完成。

## 2. 阶段流程与门禁

### 2.1 需求分析

输入：课程任务书、原始三份Word文档、平台截图、模拟数据。

活动：

1. 梳理角色、数据源、主题、指标、页面和边界。
2. 区分“必须、应当、可选、明确不做”。
3. 把验收硬指标转为可测试条目。
4. 形成需求基线并建立追踪矩阵。

输出：`docs/需求规格说明书.md`、指标清单、成果物清单。

退出条件：范围无歧义；至少30项指标有口径；不可算项说明字段缺口；验收标准可度量。

### 2.2 系统设计

活动：

1. 概要设计确定架构、技术选型、分层、模块边界。
2. 详细设计确定表、主键、索引、API、公式和错误码。
3. 设计评审检查需求覆盖、数据安全、可测试性与过度设计。
4. 形成DDL和接口约定。

输出：`docs/概要设计说明书.md`、`docs/详细设计说明书.md`、`sql/`。

退出条件：需求追踪无孤立项；敏感字段处理有明确方案；所有必须需求有实现路径。

### 2.3 任务拆分与计划

按数据、后端、前端、智能分析、测试、部署分组。每项任务至少包含：

- 明确交付物和验收条件。
- 依赖任务。
- 测试方式。
- 风险与未决事项。

输出：`docs/开发计划与进度记录.md`。

### 2.4 开发环境与版本控制

环境基线：

- Python 3.11+，Node.js 20+，npm。
- 依赖锁定于 `backend/requirements.txt`、`frontend/package-lock.json`。
- 环境变量由 `.env.example` 说明，不提交真实密钥。

建议分支模型：

| 分支 | 用途 | 合并目标 |
|---|---|---|
| `main` | 可演示、可验收版本 | 无 |
| `develop` | 集成开发 | `main` |
| `feature/*` | 单功能开发 | `develop` |
| `fix/*` | 缺陷修复 | `develop` |
| `release/*` | 验收前冻结与修复 | `main`、`develop` |
| `docs/*` | 文档与成果物 | `develop` |

提交信息建议：`feat(metrics): add outpatient per-patient visits`、`fix(etl): prevent weekly ADS overwrite`。

> 当前交付目录尚未初始化正式Git仓库和提交历史，因此分支规范是交付后的协作规范，不能宣称已执行分支评审。

### 2.5 数据开发流程

1. 获取授权模拟数据，登记来源、行数、日期范围、字段。
2. 更新数据字典和 ODS 映射。
3. 实现/修改模板识别、标准化与校验。
4. 执行全量 ETL，核对六源行数、错误数、批次。
5. 构建 DWS/ADS，执行聚合一致性与主键测试。
6. 变更指标时更新口径手册、代码、测试和历史回刷。

禁止：直接修改运行数据库掩盖ETL错误；用硬编码数字替代计算；把缺失字段指标补0；将真实患者数据放入演示库。

### 2.6 编码规范

- Python：PEP 8，函数小而单一，SQL参数化，异常分类处理。
- Vue：单文件组件，`script setup`，页面/组件/工具分层。
- API：统一响应、明确状态码、所有业务路由鉴权。
- 注释只解释意图和边界，不复述代码。
- 禁止在源码、日志、前端和数据库保存LLM Key或密码明文。

### 2.7 测试流程

```text
单元测试 → 接口测试 → 数据对账 → 前端构建
→ 浏览器E2E → 性能/安全 → 验收演示
```

要求：

1. 新功能必须新增或修改测试。
2. 后端覆盖率不得低于80%，当前通过门槛。
3. 指标变更必须做源数据复算。
4. 50问评测准确率低于85%时阻断发布。
5. 测试失败不得通过降低断言或跳过用例“修复”。

### 2.8 代码评审

评审清单：

- 需求是否完整实现，是否存在隐式范围缩减。
- SQL是否参数化，权限是否在服务端强制。
- 是否泄露患者身份或密钥。
- 指标分母、去重、时间边界是否正确。
- 错误和空值是否可解释。
- 是否补充测试和文档。
- 是否引入不必要依赖。

输出：`docs/代码评审记录.md`。严重问题未关闭不得合并。

### 2.9 发布与回滚

发布前：

1. 全量测试通过。
2. 备份数据库。
3. 记录数据批次、代码版本、配置和测试结果。
4. 执行健康检查和关键页面冒烟。

回滚：

- 应用回退到上一版本。
- 数据库使用发布前备份恢复。
- ADS可按区间重新回刷，DWS可全量重建。
- 回滚后必须记录原因和影响范围。

### 2.10 验收与归档

验收依据需求基线、测试报告、成果物清单。验收输出：

- 已通过项及证据。
- 有条件通过项及整改期限。
- 未通过项及影响。
- 签字/日期（课程由教师或指定验收人完成）。

归档目录必须包含源码、SQL、初始化数据、文档、测试证据和部署配置；数据库、密钥和视频按交付要求单独处理。

## 4. 缺陷管理流程

| 等级 | 定义 | 处置时限（课程建议） |
|---|---|---|
| S1 阻断 | 数据错误、越权、无法启动、密钥泄露 | 立即停止演示并修复 |
| S2 严重 | 核心指标错误、导出失败、权限绕过 | 当轮修复并回归 |
| S3 一般 | 非核心页面错误、格式问题 | 验收前修复 |
| S4 建议 | 体验和文档优化 | 可列入后续计划 |

流程：发现 → 记录复现步骤 → 定级 → 分派 → 修复 → 回归 → 关闭。缺陷清单见 `docs/测试用例与缺陷清单.md`。

## 5. 文档与配置管理

- 文档版本与需求基线同步，过期描述必须删除或标注历史。
- 文档中的数字必须能从代码或测试输出复现。
- `.env`、数据库、日志、备份不进入代码库。
- 初始化维度与指标快照由 `scripts/export_init_data.py` 生成。
- 每次交付更新 `docs/成果物清单.md`。
