# 部署运维手册

## 1. 部署定位

本手册覆盖本机开发与Docker Compose演示部署。当前配置使用HTTP、演示账号和单容器SQLite，不是生产高可用方案。本次材料编写未执行容器构建或部署验收，相关验证状态见《测试计划与报告》。

## 2. 环境要求

- 本地：Python 3.11+、Node.js 20+、npm；后端依赖见 `backend/requirements.txt`。
- 容器：支持Compose v2的Docker环境。
- 端口：后端8765，前端5173。启动前应确认端口未被占用。
- 文件：六份模拟CSV必须保持 `data/mock_his` 与 `data/files` 的目录结构；数据库父目录需可写。

## 3. 配置项

| 环境变量 | 默认值 | 运维说明 |
|---|---|---|
| `MEDICAL_DATA_DIR` | 项目 `data` | 六源文件根目录；附加12个月模式可指向 `data/supplemental_12m`，默认主题不要设置 |
| `MEDICAL_DB_PATH` | 项目 `data/derived/medical_ops.db` | 本地数仓文件路径；多实例不要意外共享同一文件 |
| `MEDICAL_SECRET_KEY` | `dev-only-change-me` | JWT HMAC密钥，演示默认值必须替换 |
| `MEDICAL_TOKEN_MINUTES` | `480` | 登录令牌有效分钟数 |
| `MEDICAL_HASH_SALT` | `local-course-project` | 患者标识散列盐；首次ETL前固定，变更会改变所有新计算的patient_key |
| `LLM_PROVIDER` | `deepseek` | `deepseek` 或 `kimi` |
| `DEEPSEEK_API_KEY` / `KIMI_API_KEY` | 空 | 对应供应商Key；留空即本地规则 |
| `DEEPSEEK_BASE_URL` | `https://api.deepseek.com/v1` | DeepSeek兼容接口地址 |
| `DEEPSEEK_MODEL` | `deepseek-chat` | DeepSeek模型名 |
| `KIMI_BASE_URL` | `https://api.moonshot.cn/v1` | Kimi兼容接口地址 |
| `KIMI_MODEL` | `moonshot-v1-8k` | Kimi模型名 |
| `CORS_ORIGINS` | 本地5173两个来源 | 英文逗号分隔的精确来源列表 |

`.env.example` 只是样例。本地Python不会自动加载 `.env`，需通过Shell导出；Compose命令从项目根运行时会读取根目录 `.env` 完成变量替换。不要把真实 `.env`、数据库或备份提交到版本库。

## 4. 本地运行

完整Linux/macOS、Windows PowerShell与Git Bash命令见根目录 `README.md`。核心顺序固定为：

1. 创建虚拟环境并安装后端依赖。
2. 从项目根执行 `PYTHONPATH=backend .venv/bin/python -m etl.jobs.pipeline`；Windows使用 `.venv/Scripts/python.exe` 或PowerShell等价命令。
3. 以 `app.main:app` 启动Uvicorn，监听 `127.0.0.1:8765`。
4. 在 `frontend/` 安装依赖并启动Vite，端口5173。

Linux/macOS辅助脚本：

```bash
bash scripts/start_backend.sh
# 另一个终端
bash scripts/start_frontend.sh
```

脚本不会自动安装依赖或执行ETL，避免在每次启动时隐式改写数仓。

## 5. Compose演示部署

从项目根执行：

```bash
cp .env.example .env
# 修改 MEDICAL_SECRET_KEY 与 MEDICAL_HASH_SALT；按需配置一个LLM供应商。
docker compose -f deploy/docker-compose.yml build
docker compose -f deploy/docker-compose.yml run --rm backend python -m etl.jobs.pipeline
docker compose -f deploy/docker-compose.yml up -d
docker compose -f deploy/docker-compose.yml ps
```

访问：

- 前端：http://127.0.0.1:5173
- 后端：http://127.0.0.1:8765/health
- API文档：http://127.0.0.1:8765/docs，也可经前端Nginx访问 http://127.0.0.1:5173/docs

容器布局：

- 后端工作目录 `/app`，`PYTHONPATH=/app/backend`，监听容器内 `0.0.0.0:8765`。
- 六份源CSV被复制进镜像；运行期数据库位于 `/app/data/derived/medical_ops.db`。
- 命名卷挂载 `/app/data/derived`，用于保留SQLite及上传临时目录。上传接口最终在 `finally` 中删除临时文件。
- 前端采用Node构建、Nginx运行的多阶段镜像；Nginx提供SPA回退，并代理API、健康检查和Swagger资源。
- 前端Nginx允许25 MiB请求体以容纳multipart开销，应用自身仍限制上传文件20 MiB。

重新执行ETL：

```bash
docker compose -f deploy/docker-compose.yml run --rm backend python -m etl.jobs.pipeline
```

全量ETL会重建八张主题DWS、`dim_date`和ADS的日/周/月结果。若只需重算指定区间：

```bash
docker compose -f deploy/docker-compose.yml run --rm backend python -m etl.jobs.ads_refresh --start 2025-05-01 --end 2025-05-31 --grains day,week,month
```

也可由管理员/分析师调用 `POST /api/v1/etl/ads/refresh`，请求体字段为 `start`、`end`、`grains`、`dept_code`。回刷按完整日/周/月桶执行，重复运行幂等；当前30项可算指标全部预计算，共35,640行，K25缺少上年数据时保存NULL。

查看日志：

```bash
docker compose -f deploy/docker-compose.yml logs --tail=200 backend
docker compose -f deploy/docker-compose.yml logs --tail=200 frontend
```

停止服务但保留卷：

```bash
docker compose -f deploy/docker-compose.yml down
```

`down -v` 会删除数据卷，属于破坏性操作；除非已备份并明确要清空数仓，否则不要使用。

## 5A. 测试、对账与安全脚本

在服务启动后可从项目根执行：

```bash
# 源CSV → DWD → DWS → ADS全链路对账
.venv/Scripts/python.exe scripts/check_reconciliation.py

# HTTP安全冒烟（13项）
.venv/Scripts/python.exe scripts/security_check.py

# 8并发120请求本机压测，不是生产容量测试
.venv/Scripts/python.exe scripts/load_test.py --workers 8 --requests 120

# Edge无头E2E，要求前端5173、后端8765均运行
node frontend/e2e/smoke.mjs
```

报告分别写入 `data/derived/reconciliation_report.json`、`security_check_report.json`、`load_test_report.json`、`e2e_report.json`。

## 6. 健康检查与排障

| 现象 | 检查顺序 |
|---|---|
| 前端无法连接 | 后端 `/health`、8765端口、Vite代理、Nginx后端名称与容器网络、浏览器请求Trace ID |
| 启动后无指标 | 是否先执行ETL、`MEDICAL_DB_PATH` 是否指向同一文件、ETL输出是否含错误 |
| 登录失效 | 令牌是否过期、后端密钥是否在重启后变化、用户是否enabled |
| 科室用户403 | 用户科室范围是否仅HN、请求 `dept_code` 是否越权 |
| 导入422 | 模板必填字段、日期格式、数值和负数、同主键不同内容、文件类型 |
| 导入413 | 应用20 MiB限制；Nginx更大的请求限制不代表应用放宽 |
| LLM回退 | Provider与Key是否匹配、出向网络、Base URL、模型名、供应商响应；无Key回退是正常设计 |
| SQLite锁定或写入失败 | 目录写权限、磁盘空间、是否有其他进程占用；不要删除WAL/SHM文件来“修复” |

每个JSON响应带 `trace_id`，HTTP响应带 `X-Trace-ID`。管理员可通过 `/api/v1/audit/logs` 查看登录、查询、导入、导出、ETL与AI操作审计；审计不是完整的系统日志替代品。

## 7. 数据质量与重跑

- 导入时记录关键字段完整性和业务主键唯一性结果。
- 管理员或分析师调用 `POST /api/v1/quality/run` 可执行10项规则，包括日期逻辑、非负金额、科室/病种映射和LIS值域。
- `latest_quality` 的分数按失败行占总检查行数计算，不是完整的医院数据质量成熟度评分。
- ETL任务的cron字符串目前仅作展示；需要真实调度时，应由受控外部调度器调用命令或接口，并防止并发重跑。
- 重跑是业务主键替换加汇总重建，不会删除源文件中已消失的历史DWD记录。需要“清空重建”时，必须先备份并设计独立、经确认的恢复流程。

## 8. SQLite备份与恢复

备份应使用SQLite在线备份API或确认服务完全停止后的文件级副本；运行中只复制主 `.db` 文件可能遗漏WAL内容。备份文件与源CSV一样需要限制访问，因为ODS仍含原始模拟身份字段。

本地在线备份示例（从项目根执行，目标路径可调整）：

```bash
PYTHONPATH=backend .venv/bin/python -c "import sqlite3; from app.core.config import DB_PATH; src=sqlite3.connect(DB_PATH); dst=sqlite3.connect('medical_ops_backup.db'); src.backup(dst); dst.close(); src.close()"
```

恢复前应停止写入、核对备份完整性并保留当前文件。容器卷恢复不能直接照搬本地相对路径，应先在临时卷或临时数据库中验证，再制定明确的停机和替换步骤。当前项目没有自动备份、自动恢复或容灾能力，恢复演练状态为待更新。

## 9. 生产化前置项

若未来从教学演示转向真实环境，至少需要：替换默认账号与密钥、HTTPS和可信反向代理、登录限流与凭据轮换、令牌存储安全评估、ODS原文加密和访问审计、数据最小化与留存策略、外部LLM合规审批、集中日志、自动备份恢复演练、迁移管理、并发与容量测试、正式维度主数据、财务对账以及官方DRG/DIP能力。未完成这些事项前，不得声称通过生产验收。
